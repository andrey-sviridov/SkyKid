# Модели данных SkyKid

## Погодные модели

### RawWeatherObservation (`Core/Models/RawWeatherObservation.swift`)

Транспортная модель адаптеров. Все погодные значения необязательны, поэтому настоящий `0` (штиль, отсутствие осадков или UV) не смешивается с отсутствующим полем ответа. `source` хранит фактического провайдера, а `qualityOverrides` и `notes` позволяют адаптеру отметить вычисленное значение.

### NormalizedWeather (`Core/Models/NormalizedWeather.swift`)

Единственный погодный вход основного UI и TOG-пайплайна. Содержит температуру, ощущаемую температуру, влажность, устойчивый ветер и порыв, направление, осадки, WMO-код, UV, облачность, тип осадков и почасовой прогноз.

Для каждого `WeatherField` хранится `WeatherFieldStatus`:

- `source` — реальный поставщик данных;
- `origin` — провайдер, вычисление из ответа или защитная подстановка;
- `quality` — `observed`, `derived`, `estimated` либо `unavailable`;
- `note` — пользовательски понятная причина подстановки.

`WeatherConfidence` агрегирует качество полей в `high`, `medium` или `low`. Отсутствующий UV не позволяет выставить высокую уверенность, потому что солнечная поправка не подтверждена.

### WeatherSnapshot (`Core/Models/WeatherSnapshot.swift`)

`WeatherSnapshot` — версия 1 неизменяемой provenance-модели на границе рекомендации и прогулки. Она сохраняет:

- время получения (`capturedAt`) и `staleAfter`, из которых свежесть вычисляется с явно переданным `now`;
- фактического провайдера;
- обязательную температуру и optional измерения без подстановки значений;
- качество и происхождение каждого нормализованного поля, включая пояснение fallback.

Snapshot с отсутствующей или нечисловой основной температурой не создаётся. `ActiveWalk.weatherSnapshot` и `WalkLog.weatherSnapshot` optional для обратной совместимости: старые payload декодируются с `nil`, а новые записи могут сохранить provenance без зависимости хранения от сетевых DTO.

`PrecipType` и `HourlyForecast` объявлены рядом с `NormalizedWeather`: это действующие части нормализованной погодной модели и почасового окна. Удалённый legacy scalar-контейнер не участвует ни в сети, ни в расчёте, ни в декодировании сохранённых данных.

## ChildThermalProfile (`Core/Models/ChildThermalProfile.swift`)

Постоянная часть профиля:

- `name`, `gender`, `birthday`;
- `gestationalAgeWeeks` в диапазоне 22…40;
- `stableTraits: Set<StableThermalTrait>` — устойчивые особенности, а не самочувствие сегодня;
- `temperaturePreferenceOffset` в диапазоне −3…+3°C;
- вычисляемые возраст, возрастная группа и скорректированный возраст.

В текущем reviewed v1 расчёт одежды поддерживает возраст от рождения до ровно 12 месяцев. `AgeSafetyPolicy` определяет эту календарную границу единообразно для onboarding, редактирования и runtime. Старый сохранённый профиль старше границы не удаляется и продолжает декодироваться, но рекомендации для него ограничиваются до изменения даты или перехода к индивидуальным советам врача.

`StableThermalTrait`: `frequentIllness`, `coldSensitive`, `heatSensitive`, `anemia`, `atopicDermatitis`, `cardioRespiratory`.

## WalkContext (`Core/Models/WalkContext.swift`)

Временный вход для одной планируемой прогулки:

- `healthStatus` и необязательная `bodyTemperatureCelsius`;
- `activityLevel`, `walkType`, `transportMode`;
- капюшон, дождевик, конверт, плед и слинг под курткой;
- `availableGarmentIDs` — снимок личного гардероба для текущего расчёта.

`WalkContext` не реализует `Codable`. `WalkContextStore` хранит его только в памяти текущего запуска. Острая болезнь и выбор транспорта не попадают в `UserDefaults` и App Group.

## ChildProfile (`Core/Models/ChildProfile.swift`)

`ChildProfile` — миграционная обёртка над `ChildThermalProfile`. Схема v3 кодирует `schemaVersion`, стабильный `id` и `thermalProfile`. При декодировании старого плоского JSON:

Профиль также содержит стабильный `id: UUID` (схема v3). Он генерируется при декодировании старого payload без `id`, затем сохраняется при следующей записи и переживает переименование ребёнка. В single-child v1 это единственный идентификатор персонализации; имя и дата рождения больше не используются как текущий ключ.

- устойчивые особенности и срок рождения мигрируют;
- лихорадка, ОРВИ, активность, тип прогулки и коляски намеренно отбрасываются.

Сохранение: `ChildProfileStore.shared.profile` → App Group (`child_profile`, JSON v3).

## AppGroup (`Core/Models/ChildProfile.swift`)

Enum-пространство имён; методы статические, обращаются к `UserDefaults(suiteName: "group.com.skykid.app")`.

| Метод | Описание |
|---|---|
| `saveProfile(_:)` / `loadProfile()` / `deleteProfile()` | Профиль ребёнка (Codable JSON) |
| `saveWeather(temperature:apparentTemp:weatherCode:windSpeed:precipitation:cityName:)` | Кеш погоды |
| `loadCachedWeather() → CachedWeather?` | nil если > 2 ч или пуст |

**App Group capability** должна быть включена для обоих таргетов с ID `group.com.skykid.app`.

## OutfitRecommendation

`OutfitRecommendation` — единый Codable-результат для основного UI, журнала прогулок, виджета и Siri.

| Поле | Описание |
|---|---|
| `temperatures.outside` | Измеренная наружная температура |
| `temperatures.apparent` | Ощущаемая температура провайдера |
| `temperatures.effective` | Поправки ветра, влажности, осадков и солнца |
| `temperatures.microclimate` | Условия ребёнка в коляске, слинге или автокресле |
| `layers`, `accessories` | Слои из `OutfitSolver` без UI-адаптации |
| `missingGarments` | Необязательный для декодирования список подходящих, но отсутствующих вещей; UI показывает его как варианты замены |
| `totalTOG`, `targetTOG` | Сухое утепление комплекта и тепловая цель |
| `fit` | Эффективный TOG, погрешность, покрытие корпуса и уверенность |
| `warnings`, `checkHint`, `walkWindow` | Выход safety-движка |

## OutfitRecommendationSnapshot

`OutfitRecommendationSnapshot` оборачивает полный `OutfitRecommendation` и добавляет `schemaVersion`, `algorithmVersion`, `generatedAt`, `expiresAt`, имя/возраст ребёнка, город и optional `RecommendationSnapshotContext`. `algorithmVersion` — семантическая версия поведения детерминированного расчёта, независимая от схемы хранения и marketing version приложения. Текущее значение задаёт `RecommendationAlgorithmVersion.current`; при изменении формул или safety-правил оно увеличивается. Отсутствующее поле в старом payload означает legacy/unknown (`nil`), а не версию, выведенную из версии приложения. Контекст содержит описание погоды, источник, уверенность, транспорт, активность и тип прогулки; optional сохраняет декодирование снимков ранней схемы v2.

`generatedAt` соответствует моменту получения использованной погоды, а не любому локальному пересчёту комплекта. Поэтому смена гардероба, транспорта или персональной поправки сохраняет прежний `expiresAt` и не продлевает актуальность старого прогноза. `AppGroupRecommendationSnapshotStore` хранит снимок под ключом `outfit_recommendation_snapshot_v2`; TTL по умолчанию — два часа.

## Модели персонализации

`WalkOrigin` кодирует происхождение записи: `tracked` для завершённого таймера и `manual` для записи задним числом. Старые payload без поля выводят origin из `isLiveTracked`; отсутствие достаточной provenance всё равно делает их нетренирующими.

`PersonalizationEligibility` вычисляется чистым evaluator-ом и не редактируется UI. Для thermal training запись должна быть живой (`tracked`), иметь валидный свежий `WeatherSnapshot` с известным происхождением и полный контекст (`microclimateTemperature`, транспорт, активность и тип прогулки). Иначе сохраняется аудируемая причина исключения (`manualWalk`, `missingWeatherSnapshot`, `staleWeatherSnapshot`, `unknownWeatherProvenance`, `missingWalkContext` и т.д.). Manual-записи остаются в истории, но не создают observations.

`PersonalizationContext` сохраняет условия, в которых родитель оценил комплект: `microclimateTemperature`, `TempBand`, транспорт, активность, тип прогулки, возрастную группу, класс погоды, диапазоны утепления и длительности, одежду, целевой/фактический TOG и optional изменение одежды. Признаки представлены закрытыми enum-бакетами, а не произвольным feature-словарём. Новые optional-поля декодируются из старой схемы без выдуманных значений. При синхронизации журнала контекст не подставляется из `WalkContext.standard` или текущей погоды.

`PersonalizationObservation` связывает контекст с `UserFeedback`, временем, источником и стабильным `sourceID`. Быстрый отзыв использует ID текущей сессии, а журнал — `WalkLog.id`; повторная запись с тем же ID заменяет прежнее наблюдение.

`PersonalizationProfileState` — Codable-схема v2:

| Поле | Назначение |
|---|---|
| `schemaVersion` | Версия сохранённого формата |
| `legacyOffsetsByBand` | Baseline, мигрированный из `tog_offset_v1` |
| `observations` | Не более 80 последних контекстных оценок |

`PersonalizationSummary` — read model для UI: текущая зона/сценарий, применённая ограниченная поправка, число похожих прогулок и независимых направленных сигналов, подтверждения «Комфортно», признак сохранённых данных и `PersonalizationExplanation`. При недостаточных или смешанных данных explanation остаётся честным и не выражается процентом.

`PersonalOffsetStore` хранит новые состояния под UUID профиля. При первом обращении legacy-состояние, сохранённое под ключом нормализованных имени и даты рождения, переносится в UUID ровно один раз: после успешной записи исходные ключи удаляются. `feedbackHistory(for:limit:)` возвращает только наблюдения выбранного профиля за допустимый срок, от новых к старым. `FeedbackHistoryItemBuilder` переводит их в presentation-модель истории, не изменяя персонализацию.

`WalkLog` дополнительно хранит `algorithmVersion` и optional-контекст персонализации. Новые записи получают текущую semantic version, а старые JSON-записи декодируются с `algorithmVersion == nil` (legacy/unknown). Поля контекста optional для обратной совместимости со старыми JSON-записями; при редактировании старой прогулки доступный контекст дополняется.

### Активная прогулка и завершение

`ActiveWalkStore` хранит ровно одну активную прогулку под ключом `active_walk_v1`. `start(_:)` не перезаписывает существующую запись и возвращает явный результат `alreadyActive`. После перезапуска сохранённая прогулка восстанавливается с исходными `id` и `startDate`; UI предлагает продолжить её или завершить.

Продолжительность вычисляется как абсолютная разница между переданным `now` и сохранённым `startDate` и ограничивается снизу нулём. Поэтому переход приложения в фон, смена часового пояса и DST не меняют длительность, а перевод системных часов назад не создаёт отрицательное значение.

`weatherSnapshot` — неизменяемое свидетельство условий на старте. Более поздние значимые наблюдения сохраняются отдельно в `passiveWeatherUpdates`; чистая `PassiveWeatherChangePolicy` отмечает начало/окончание известных осадков либо изменение ощущаемой температуры не менее чем на 3 °C. Неизвестные осадки не интерпретируются как нулевые.

При завершении `WalkLog` хранит короткую необязательную оценку `comfortFeedback` (`cold`, `comfortable`, `hot`, `unsure`, `skipped`), изменение одежды `clothingAdjustment` и optional `adjustedGarmentID`. Legacy-поля и события продолжают декодироваться, но основной сценарий не требует событий во время прогулки. `unsure` и `skipped` не используются как сигнал персонализации.

## GarmentCatalog (`Features/Outfit/GarmentCatalog.swift`)

```swift
enum GarmentCatalog {
    static let all: [GarmentItem]                       // единственный каталог
    static let byID: [String: GarmentItem]              // O(1) lookup
    static let byLayer: [GarmentLayer: [GarmentItem]]   // O(1) по категории
}
```

`GarmentItem` хранит обе тепловые величины (`heatValue` для legacy CLO и `tog` для основного решателя), возрастную группу, назначение `GarmentUse`, `coveredZones`, анатомические слоты слоя и `exclusiveGroup`. `GarmentCompatibilityPolicy` является единственным местом проверки совместимости. Скрытых предметов с `catalogAgeGroup == nil` больше нет.

`BodyZone`: корпус, руки, ноги, голова, шея, кисти и стопы. `GarmentUse` отделяет прогулочную одежду, аксессуары, утепление коляски, сон и утилитарные предметы.

Старый `WardrobeModel` и его ручной CLO-конструктор удалены. Выбор доступных вещей для основного сценария выполняется через `UserWardrobeStore` и `OutfitSolver`.

`UserWardrobeStore` хранит два множества: `confirmedOwnedIDs` и `unavailableIDs`. ID, отсутствующий в обоих множествах, имеет состояние `unknown`; новые позиции каталога остаются неизвестными. Для solver неизвестные вещи остаются кандидатами, а исключаются только явно недоступные. Поэтому рекомендация может показать неизвестную вещь и ненавязчиво спросить «Есть / Нет», не требуя предварительно заполнять весь гардероб.

Миграция схемы v5 распознаёт legacy-состояние, автоматически заполненное всем каталогом, и переводит его в `unknown`. Если старый пользователь изменял чек-лист, выбранные позиции сохраняются как `owned`, а снятые — как `unavailable`. Подгузник остаётся обязательным техническим ID. Мёртвые ID отбрасываются, canonical-ID сохраняются, а явные ответы не стираются при добавлении новых предметов.

## Локальная резервная копия

`SkyKidBackup` schema v2 — переносимый JSON-контейнер для данных пользователя:
профиль со стабильным UUID, прогулки с weather provenance и версией алгоритма,
состояния персонализации, tri-state гардероб, язык и тема. Погодный кэш,
координаты, активная прогулка и API-ключи намеренно не экспортируются.

Импорт v1 сначала мигрируется в памяти, затем весь документ валидируется.
Restore использует явную стратегию replace, не merge: запись начинается только
после подтверждения пользователя, а ошибка любого шага возвращает предыдущий
снимок. Future schema отклоняется без изменения данных.
